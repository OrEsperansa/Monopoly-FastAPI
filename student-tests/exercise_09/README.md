# תרגיל 9: פשיטת רגל, ניצחון ואיפוס

## מטרת התרגיל

להשלים את מחזור החיים של המשחק ולוודא שכל היכולות מהתרגילים הקודמים פועלות יחד דרך HTTP בלבד.

## פשיטת רגל וסיום המשחק

- כאשר כסף של שחקן יורד מתחת ל-0, ‏`is_bankrupt` שלו הופך ל-`true`.
- שחקן שפשט רגל אינו מקבל תורות נוספים.
- כאשר נשאר שחקן אחד בלבד שאינו פושט רגל, `status` הופך ל-`finished`.
- `winner_id` מקבל את מזהה אותו שחקן; המזהה חייב להופיע ברשימת השחקנים.
- במצב `finished`, ‏`available_actions` היא רשימה ריקה.
- כל פעולת משחק נוספת, מלבד איפוס, מחזירה `409` עם הודעה מתאימה שמסבירה את השגיאה ואינה משנה את תוצאת המשחק.
- איזון הלוח וההשפעות חייבים לאפשר למשחק אמיתי להגיע למנצח. בדיקת הקבלה מריצה לכל היותר 2,000 תורות ואינה כופה תוצאות קובייה.

## נקודת הקצה החדשה

### `POST /api/game/reset`

הבקשה אינה כוללת גוף. התגובה מחזירה `200` ואובייקט עם המפתח היחיד `state`. המצב המאופס חייב להכיל בדיוק את `GameState` ולהחזיר:

```json
{
  "state": {
    "status": "not_started",
    "current_player_id": null,
    "winner_id": null,
    "available_actions": [],
    "players": [],
    "board": [],
    "last_event": "Game reset.",
    "event_log": ["Game reset."]
  }
}
```

הטקסט המדויק של אירוע האיפוס יכול להיות שונה, אך `last_event` חייב להיות זהה לאיבר האחרון ב-`event_log`.

## מבנה המערכת המלא

כל נקודות הקצה מתרגילים 1–8 ממשיכות לפעול. השרת הוא מקור האמת היחיד לכסף, מיקום, בעלות, תור, פעולות זמינות, אירועים, פשיטת רגל ומנצח. ה-UI רק מציג את המצב ושולח פעולות שהשרת מתיר.

## כיצד לוודא שהתרגיל הושלם

הריצו משחק מלא עם קובייה אקראית, קניות וסיום תורות עד `finished`. ודאו שנותר שחקן פעיל אחד, שהוא `winner_id`, ושאין פעולות זמינות. לאחר מכן בצעו reset והשוו את כל שמונת השדות לדוגמה המלאה למעלה.
